# 月账单列表耗时调查（PORTALBIG，约 360 ms）

只调查，调查阶段没有改应用代码。基线 `192dabc`（origin/main，#62 已合并），日期 2026-10-23。处理结论与复测见[第 8 节](#8-处理与复测)。

原始证据在 [statement-list-latency/](statement-list-latency/)（文件内是英文原始输出）：计划、各变体的热 / 冷耗时、HTTP 复跑、单次请求的语句追踪、SQL 变体、node 原型。

## 结论

假设成立，设计文档的估算需要更正。

- 一条 SQL（进行中月份的 `computeStatement`）占列表请求数据库时间的 99%（365 ms 里的 362 ms）。请求里其余九条语句合计 2.8 ms，没有 N+1；HTTP、认证、JSON 另约 17 ms。
- 设计文档按单项相加估的约 150 ms，对「预期的计划」是对的。实际语句的计划差得多：**期初余额对整张 `ledger_entries`（290 万行）做了两次顺序扫描，占语句的 63%**，估算里没有这一项。
- 列表还算了用不上的国家、日明细（`figuresOf` 只留 8 个标量），占 32%。
- 改语句的写法（约 20 行）：语句从 353 ms 降到 104 ms，数字完全相同；只算列表要的数字可降到 42 ms。

## 2. 时间花在哪

### 请求层

服务端日志（`log_min_duration_statement = 0`，[list-request-queries.txt](statement-list-latency/list-request-queries.txt)）：一次列表请求十条语句，九条各 0.001 至 0.435 ms，实时行那条 362.3 ms。只有一个月份实时算（其余 12 个月份一条头部查询读出），没有 N+1，头部与行之间没有重复计算。真实应用路径（drizzle 加 node-postgres）上的 `auto_explain` 与 psql 的计划相同，所以下面 psql 的测量可信（psql 358 ms，服务端日志 362 ms，HTTP 370 ms）。

### 语句层

`fs_billing_app` 带租户 RLS，热，10 次中位数（[hot-timings.txt](statement-list-latency/hot-timings.txt)）；各部分是同一段 SQL 单独跑。

| 语句的部分                                    | ms    | 占比 |
| --------------------------------------------- | ----- | ---- |
| 期初余额锚点，**执行两次**（2 x 112.5）       | 225.0 | 63%  |
| `by_day`（话单排序 128,795 行并落盘，再分组） | 57.7  | 16%  |
| `by_country`（同上）                          | 57.0  | 16%  |
| `flows`（本月流水四项合计）                   | 18.0  | 5%   |
| 各部分之和                                    | 357.7 |      |
| 整条语句实测                                  | 358.1 |      |

各部分相加等于整体，别的开销可忽略：规划约 1.5 ms（热连接的 bind 时间），jsonb 拼装与 CTE 扫描不到 0.1 ms。

## 3. 根因

### 3.1 期初锚点是整表顺序扫描，而且扫两次（225 ms）

`compute.ts` 把边界放在 `bounds` CTE 里，用 `(select lo from bounds)` 引用。InitPlan 的值在规划时未知，`occurred_at >= (select lo from bounds)` 按默认不等式选择度（三分之一）估算；PORTALBIG 占整表 97%，估出 475,798 行（实际 128,797），顺序扫描比索引便宜。计划（[current-statement-explain.txt](statement-list-latency/current-statement-explain.txt)）：

```
InitPlan 18  Seq Scan on ledger_entries  rows=475798（实际 128797），Rows Removed by Filter: 2807174，每次读约 5 万页   约 115 ms
InitPlan 27  Seq Scan on ledger_entries（同一个子查询再来一遍）                                                     约 110 ms
flows        Index Scan using ledger_entries_tenant_occurred_at，估 7137 行（实际 128797）                          约 12 ms
```

三个原因叠加：

1. **边界被藏起来。** 同一个锚点换成字面量边界就是索引范围扫描：11.0 ms，不是 112.5 ms。设计文档当时单独测的 9 至 104 ms 正是这种写法，所以看起来没问题。
2. **执行了两次。** `opening` 只被引用一次，被内联；`o.amount` 在 select 列表里出现两次（`opening_balance` 与 `closing_balance`），每处各成一个 InitPlan。
3. **RLS 禁用并行。** `app_scope()`、`app_tenant_id()`、`app_is_operator()` 是 `STABLE` 但 `PARALLEL UNSAFE`（默认），`fs_billing_app` 对任何 RLS 表的扫描都只能单进程。同一个锚点用表 owner（无 RLS）跑是 Parallel Seq Scan：41.7 ms，不是 112.5 ms；整条语句 owner 下 208 ms，不是 358 ms。修复后 RLS 仍有开销：每扫 12.9 万行约 3 ms，加上并行丢失（第 5 节）。

只伤大租户的原因：只有一个租户占满整表时规划器才会换成顺序扫描。PORTALS1（28,578 笔流水）列表只要 8.8 至 9.5 ms。

### 3.2 列表算了不显示的明细（用不上的约 80 ms；两遍共 115 ms）

`readStatementMonthList` 对实时行调用 `computeStatement`，再由 `figuresOf(live)` 只留 `openingBalance、recharge、gift、adjustment、callCharges、closingBalance、calls、callMinutes`。语句还拼了国家数组、日数组与 `breakdown_gap`，列表都不用。按日那一遍全是白算（57.7 ms）；按国家那一遍只为 `calls` 与 `callMinutes`，直接合计 34.2 ms，不是 57.0 ms。两个聚合还：

- 对 128,795 行做外部归并排序并落盘（`Sort Method: external merge Disk: 3720kB` 与 `3032kB`，`work_mem` 4 MB），因为藏起来的边界让规划器估成 37 行而选了排序分组；
- 在 started_at 索引上扫完租户整个 9 月的范围只为找 2 行（`Rows Removed by Filter: 246573`，各约 15 ms），因为边界未知时 31 天的 started_at 保护下界裁不掉分区。

### 3.3 设计文档为什么说约 150 ms

文档的表是字面量时间戳下单项测量值相加（flows 37、国家 39、日 56、锚点 9 至 104 ms），对预期计划大致不错（我用字面量边界的变体，锚点只算一次：103 ms）。实现的语句有三处不同：边界藏在 CTE 里（顺序扫描，112 ms 而不是 11 ms）、锚点算两次、排序落盘。

## 4. 其他发现

- **冷启动差得多。** 冲掉容器页缓存后，当前语句首次执行 0.5 至 1.2 s（496、507、533、1096；更早几次冲刷 1027、1070、1171），之后 360 ms。顺序扫描要读约 400 MB 流水堆，`shared_buffers` 只有 128 MB，每次都经页缓存重读（[cold-timings.txt](statement-list-latency/cold-timings.txt)）。
- **没有存下账单的月份才是真正的伸缩风险。** 它们按 ledger 模式实时算（期初是该月之前全部流水合计，约 250 万行的顺序扫描，205 ms，同样算两次）。2026-09 账单缺失时门户列表 1256.2、1021.5、1013.9 ms（连续三次；每月 1 日 00:00 到 02:00 的任务之间，或任务失败时会遇到）。从副本里删掉 5 个旧月份，列表 2.57 至 2.62 s（每缺一个月约 +442 ms）。账单生成任务回溯 24 个月为止，而列表从第一个月份开始走，所以历史超过 24 个月的租户这类月份是永久的。基线里 Worker 逐月生成（440 至 707 ms）用同一条 ledger 模式语句，与同样的双重扫描（2 x 205 ms）吻合。
- 耗时随当月话单量增长。同一条余额锚点语句算完整的 9 月（234,277 通；锚点尾部覆盖 9、10 月）是 466 ms，只算列表要的数字是 92 ms（[prototype-timings.txt](statement-list-latency/prototype-timings.txt)）。副本数据止于 2026-10-17，所以月末的进行中行会比这里测的 360 ms 更慢。

## 7. 建议

**先做 A，单独一个小 PR**（「让规划器看到月份边界，期初只算一次」）：每行收益最大（约 250 ms），没有行为变化，也顺带去掉冷启动与待生成月份的倍数。**B 作为后续 PR**，只在约 120 ms 不够用时再做：它要多写等价性测试和第二条代码路径，而 A 合并后设计里 500 ms 的页面目标已经满足。A 与 B 互相独立，叠加到 42 ms。

另外，与速度无关：要决定列表怎样对待没有存下账单的旧月份（第 4 节），即使 A 把代价减半，每个月份仍约 440 ms。办法是用后台重新生成补齐，或者不再在列表里实时算它们。

随后设计文档（`docs/phase-7-design.md` 性能一节与 597 行）里「推测」要换成这里的根因与新数字。

## 8. 处理与复测

用户 2026-10-23 确认：采用方案 A；取消 24 个月补生成上限（`STATEMENT_BACKFILL_MONTHS`），Worker 从租户第一个应有月份起补全所有已结束月份，列表里实时算的待生成月份于是只在刚结束到生成之间短暂出现；本文翻成中文并入库；复测。落实与数字见 [README](README.md#月账单取数优化后的耗时)：门户列表 370 到 113 ms，后台标签页 363 到 100 ms，进行中详情 379 到 111 ms，Worker 逐月生成 594 至 1884 到 120 至 437 ms。

## 9. 方法与局限

- 副本 `fs_billing_perf_inv`（`fs_billing_perf_pr3_uuid_v4` 的副本），用仓库的 migrate 脚本迁移，已结束月份用 #62 脚本生成（脚本会删旧夹具账单，并只在副本里加门户账号与会话）。结束后删除；其他库没有改动。
- 热 = 页缓存已热；Docker（OrbStack）里的 PostgreSQL 17.9，`shared_buffers` 128 MB，`work_mem` 4 MB，语句内 `jit` 关闭（同代码）。冷 = 在容器里写再读一个 7 GB 的一次性文件冲掉页缓存，每次冲掉多少流水不同，所以是一个范围。
- 单连接、没有并发负载、一台机器。`PARALLEL SAFE` 的测试在回滚的事务里。副本数据止于 2026-10-17，实时行是 128,795 通，不是整月。
