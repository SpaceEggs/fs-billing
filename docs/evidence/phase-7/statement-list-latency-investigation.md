# Monthly statement list latency (PORTALBIG, about 360 ms): investigation

Investigation only. No application code was changed. Base commit `192dabc` (origin/main, PR #62 merged). Date 2026-10-23.

Raw evidence is in [statement-list-latency/](statement-list-latency/): the plan, per-variant timings (hot and cold), the HTTP re-run, the per-request statement trace, the SQL variants and the node prototype.

## Verdict

The hypothesis is confirmed, with one correction to the design doc's estimate.

- One SQL statement, `computeStatement` for the in-progress month, is 99% of the database time of a list request (362 ms of 365 ms). Everything else in the request (nine statements, no N+1) is 2.8 ms, and HTTP, auth and JSON add about 17 ms.
- The design doc's per-part estimate (about 150 ms) was right for the plan it assumed. The implemented statement gets a much worse plan: **two sequential scans of the whole `ledger_entries` table (2.9M rows) for the opening balance, which are 63% of the statement.** That was not in the estimate.
- The list also computes per-country and per-day breakdowns that it throws away (`figuresOf` keeps eight scalars). The two passes are 32% of the statement, and about 80 ms (22%) of that is work the list never uses (the whole per-day pass, and the per-country grouping where a plain total gives the same calls and minutes).
- A minimal SQL-shape change (about 20 lines) brings the statement from 353 ms to 104 ms with identical figures. A list-only figures query brings it to 42 ms.

## 2. Where the time goes

### Request level

One list request on the server log (`log_min_duration_statement = 0`, [list-request-queries.txt](statement-list-latency/list-request-queries.txt)): ten statements, nine of them take 0.001 to 0.435 ms each. The live-row statement takes 362.3 ms. Exactly one month is computed live (the other twelve come from one header query), so there is no N+1 and no duplicated header/row work. `auto_explain` captured through the real drizzle and node-postgres path shows the same plan as psql, so the psql measurements below are faithful (psql 358 ms, server log 362 ms, HTTP 370 ms).

## 3. Root cause

### 3.1 The opening anchor is a full-table sequential scan, twice (225 ms)

`compute.ts` builds `bounds` as a CTE and refers to it as `(select lo from bounds)`. An InitPlan value is unknown at planning time, so for `occurred_at >= (select lo from bounds)` the planner uses the default inequality selectivity (one third). PORTALBIG holds 97% of the table, so it estimates 475,798 rows (actual 128,797) and a sequential scan beats the index. Plan ([current-statement-explain.txt](statement-list-latency/current-statement-explain.txt)):

```
InitPlan 18  Seq Scan on ledger_entries  rows=475798 (actual rows=128797), Rows Removed by Filter: 2807174, about 50,000 pages read   ~115 ms
InitPlan 27  Seq Scan on ledger_entries  (the same subquery again)                                                              ~110 ms
flows        Index Scan using ledger_entries_tenant_occurred_at, rows=7137 estimated (actual 128797)                              ~12 ms
```

Three compounding causes:

1. **Hidden bound.** The same anchor with a literal bound is an index range scan: 11.0 ms instead of 112.5 ms. This is also why the design doc's standalone measurement (9 to 104 ms) looked fine.
2. **Evaluated twice.** `opening` is referenced once, so it is inlined, and `o.amount` appears twice in the select list (`opening_balance` and `closing_balance`). Each copy becomes its own InitPlan.
3. **RLS blocks parallelism.** `app_scope()`, `app_tenant_id()` and `app_is_operator()` are `STABLE` but `PARALLEL UNSAFE` (the default), so every scan of an RLS table by `fs_billing_app` is single-process. The same anchor query as the table owner (no RLS) is a Parallel Seq Scan: 41.7 ms instead of 112.5 ms. The whole statement as owner is 208 ms instead of 358 ms. After the fix RLS still costs about 3 ms per scan of 129k rows plus the lost parallelism (section 5).

Why it only hurts the big tenant: the planner flips to a sequential scan only when one tenant dominates the table. PORTALS1 (28,578 ledger rows) lists in 8.8 to 9.5 ms.

### 3.2 The list computes breakdowns it does not show (about 80 ms unused, 115 ms in the two passes)

`readStatementMonthList` calls `computeStatement` for the live row and then `figuresOf(live)` keeps only `openingBalance, recharge, gift, adjustment, callCharges, closingBalance, calls, callMinutes`. The statement also builds the per-country array, the per-day array and `breakdown_gap`, all unused by the list. The per-day pass is wholly dead work (57.7 ms). The per-country pass is only needed for `calls` and `callMinutes`, which a plain total gives in 34.2 ms instead of 57.0 ms. Both aggregates also:

- sort 128,795 rows with an external merge to disk (`Sort Method: external merge Disk: 3720kB` and `3032kB`, `work_mem` 4 MB), because the hidden bounds make the planner estimate 37 rows and pick sort-based grouping;
- scan the whole September tenant range on the started_at index to find 2 rows (`Rows Removed by Filter: 246573`, about 15 ms each), because the 31-day started_at guard cannot be pruned when the bounds are unknown.

### 3.3 Why the design doc said about 150 ms

The doc's table sums standalone measurements with literal timestamps (flows 37, country 39, day 56, anchor 9 to 104 ms). Those are about right for the intended plan (my literal-bound variant: 103 ms with the anchor once). The implemented statement differs in three ways: bounds hidden in a CTE (sequential scan, 112 ms instead of 11 ms), the anchor evaluated twice, and sorts spilling to disk.

## 4. Other findings

- **Cold start is much worse.** After flushing the container page cache, the first execution of today's statement takes 0.5 to 1.2 s (496, 507, 533, 1096; earlier flushes 1027, 1070, 1171), then 360 ms. The sequential scan has to read about 400 MB of ledger heap, and with `shared_buffers` 128 MB it re-reads it through the page cache every time ([cold-timings.txt](statement-list-latency/cold-timings.txt)).
- **Months without a stored statement are the real scaling risk.** They are computed live in ledger mode (`opening` = sum of all history before the month, a sequential scan of about 2.5M rows, 205 ms, also evaluated twice). With the 2026-09 statement missing, the portal list took 1256.2, 1021.5, 1013.9 ms (three consecutive calls) (this happens between 00:00 and the 02:00 job on the 1st, or when the job fails). With five old months deleted from the copy, the list took 2.57 to 2.62 s (+442 ms per missing month). Tenants older than the 24-month backfill window have such months permanently, since `listMissingStatements` stops at 24 months while the list walks from the first month. The Worker's per-month generation (440 to 707 ms in the baseline run) uses the same ledger-mode statement and is consistent with the same double scan (2 x 205 ms).
- The cost also grows with the month's volume. The same balance-anchor statement on full September (234,277 calls; the anchor tail covers September and October) takes 466 ms against 92 ms list-only ([prototype-timings.txt](statement-list-latency/prototype-timings.txt)). The data in this copy stops on 2026-10-17, so the in-progress row at the end of a month would cost more than the 360 ms measured here.

## 7. Recommendation

Do **A first, as its own small PR** ("give the planner the month bounds and evaluate the opening once"): the largest gain per line (about 250 ms), no behavior change, and it also removes the cold-start and the pending-month multiplier. Then take **B as a follow-up PR** only if about 120 ms is not enough: it needs the extra equality tests and a second code path, and the existing 500 ms page target is already met once A is in. A and B are independent and compose to 42 ms.

Separately, and independent of speed: decide how the list should treat old months without a stored statement (section 4), since each costs about 440 ms even after A halves it. Options are to backfill them with the admin regenerate path, or to stop computing them live in the list.

The design doc (`docs/phase-7-design.md`, performance section and line 597) should then replace the "推测" note with this root cause and the new numbers.

## 8. Method and limits

- Copy `fs_billing_perf_inv` of `fs_billing_perf_pr3_uuid_v4`, migrated with the repo's migrate script, closed months generated by the #62 script (which deletes the legacy fixture statements and adds a portal account and sessions to the copy only). Dropped at the end; the other databases were not modified.
- Hot means warm page cache; PostgreSQL 17.9 in Docker (OrbStack), `shared_buffers` 128 MB, `work_mem` 4 MB, `jit` off for the statement as in the code. Cold means the container page cache flushed by writing and reading a 7 GB throwaway file; how much of the ledger was evicted varies between flushes, hence the range.
- Single connection, no concurrent load, one machine. The `PARALLEL SAFE` test was inside a rolled-back transaction. The data in this copy ends on 2026-10-17, so the live row is 128,795 calls, not a full month.
