# Phase 6 PR 2 acceptance

PR 2 replaces the administrator's per-entry balance subquery with a shared daily-merged ledger query and adds `GET /api/portal/ledger`. Customer queries use the session tenant with `withTenant`; the SQL replaces a credit recharge's internal note with `账户充值` and omits administrator and receivable joins. Administrator queries join those details after pagination. CSV export remains in PR 3, and the customer ledger page remains in PR 6.

The baseline is `2989825ab4d9f835c133c112503c1a36b70b63f5`, the merge commit of [PR #40](https://github.com/SpaceEggs/fs-billing/pull/40). Work took place on `codex/phase-6-ledger` in an isolated managed worktree. The original main checkout was clean and was not edited.

## Performance evidence

The dedicated local `fs_billing_perf` database contains the existing synthetic PORTALBIG fixture with 3,000,000 CDRs and 2,850,187 ledger entries on PostgreSQL 17.9 ARM64. The prerequisite `0015` migration was applied to this database. The migration record preserves the before and after `tenant_read` policy and the unchanged ledger count in [`perf-migration.txt`](perf-migration.txt). No fixture rows or indexes were rewritten.

`packages/db/scripts/portal-perf.ts ledger` runs the actual production query builder. It requires a separate output directory, performs no index DDL, keeps every measured sample, and writes `EXPLAIN (ANALYZE, BUFFERS)` plans. It alternates the starting variant across rounds and measures three months, both audiences, explicit `prior` and `balance` anchors, and automatic anchor choice. Each variant has two excluded warmups and seven measured samples.

The HTTP probe binds the real Fastify API to a loopback port, creates a temporary signed administrator session, and uses the real authentication gateway, authentication database role and application business role. Each fetch consumes and schema-checks the complete response. It checks HTTP 200 and at least 30 merged rows, records response bytes and counts, then deletes the temporary session. The historical 50-entry page request returns 33 merged September rows.

The first formal run is retained in [`ledger.json`](../../perf/portal-cdrs/pr2-ledger/ledger.json). Its 14 HTTP requests all returned 200, but samples of 500.8 ms and 505.1 ms exceeded the 500 ms budget. No slow sample was dropped. The preceding diagnostic run overlapped a Web test at its start, so its outputs were excluded and retained outside the repository at `/tmp/fs-billing-pr2-ledger-diagnostic-20261018`.

The first formal April administrator plan spent about 156 ms on the anchor and 288 ms on the monthly grouping. Sorting 234,254 rows required an external sort with 13,768 kB of disk. The query was then simplified to group by `(Beijing day, manual ID or NULL)`. A manual UUID identifies exactly one row, and a NULL ID group contains only that day's charges, so `max(kind)` retains the same kind. This removes repeated text-kind comparisons and places the integer date first in the grouping sort. The ordered `array_agg(id ORDER BY occurred_at DESC, id DESC)` remains in the production query.

The synthetic tenant's `created_at` is 2026-10-17, after its generated historical transactions. This makes automatic selection choose `prior` even for September. Explicit anchor measurements disclose that fixture limitation; the creation time was not changed to improve results. These are serial local measurements with warm caches. They do not establish cold-disk or concurrent-client latency.

The final day-first query passes the unchanged budget. April's seven HTTP samples have median 308.6 ms and range 303.6–368.6 ms. September's seven have median 335.8 ms and range 332.3–347.5 ms. All 14 responses returned 200 with 33 rows. The final [raw results](../../perf/portal-cdrs/pr2-ledger-day-first/ledger.json), [plans](../../perf/portal-cdrs/pr2-ledger-day-first/plans) and [stdout](perf-command-day-first.txt) are separate from the first run. No sample was discarded. The [performance report](../../perf/portal-cdrs.md#pr-2-实际合并查询与-http-实测) puts the new ordered aggregate beside the historical measurements and explains the different query scopes. [Session cleanup](perf-session-cleanup.txt) confirms no temporary sessions remain.

After aligning shared row validation and Web time formatting with the IANA `Asia/Shanghai` zone, a supplemental [HTTP-only measurement](http-timezone-validation.json) reused the real loopback API/auth/app path, consumed and schema-parsed each complete response, and ran two warmups followed by seven counted samples per month. All 14 returned HTTP 200 and 33 merged rows with no failures. April ranged 302.9–323.4 ms (median 307.5 ms); September ranged 331.6–349.2 ms (median 334.3 ms). The 500 ms budget still passes. SQL and query plans were unchanged; this is a post-validation budget check, not an A/B claim. The run was serial on a 10-core host with load averages about 2.1–2.9, and auth-session counts were 0 before and after.
