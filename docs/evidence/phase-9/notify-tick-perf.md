# notify-tick 在大表上的耗时（阶段 9 PR 4）

设计「性能」一节要求：`notify-tick` 在 10 万行 `system_alerts`、5 万行 `email_outbox` 下的耗时。

## 方法

在独立的 PostgreSQL 17.9 容器（本机、无调优）里新建空库，跑完 0000–0022 迁移，用 `generate_series` 灌入下面的数据，`ANALYZE` 之后连续调用四次 `queueNotifications`（notify-tick 的第 1–4 步，一个事务，不含 SMTP 分发）。脚本是一次性的，没有提交。

| 表              | 行数  | 构成                                                                                                                                                                                                                          |
| --------------- | ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `system_alerts` | 10 万 | 6 万已恢复的历史告警（`notify = false`）；3.9 万已恢复且开始、恢复邮件都已通知；500 条进行中、已通知、有新增事件、汇总已到期；100 条进行中、待发开始邮件；360 条进行中的历史告警；20 条 `unassigned:*`、20 条 `invalid-cdr:*` |
| `email_outbox`  | 5 万  | 4.99 万已发送（10 天前）；100 条待发                                                                                                                                                                                          |

## 结果

| 次序                | 耗时    | 认领                                                                           |
| ------------------- | ------- | ------------------------------------------------------------------------------ |
| 第 1 次             | 60 ms   | 开始 100 条、汇总 500 条（共入队 4 封：开始 1 封、汇总按每封 200 条拆成 3 封） |
| 第 2–4 次（无事件） | 约 3 ms | 无                                                                             |

三条通知查询的计划（`EXPLAIN ANALYZE`）：开始、汇总走 0020 的 `system_alerts_open`（只扫进行中的 960 行，执行 0.08 ms）；恢复通知走 0022 新增的局部索引 `system_alerts_recovery_notice`（谓词与查询一致，历史告警 `notify = false` 不在索引里，执行 0.01 ms）。没有这个索引时恢复通知查询要扫描全部已恢复的告警。

结论：稳态下每分钟的 tick 事务约几毫秒，与 10 万行告警、5 万行发件箱的规模无关；耗时随「进行中的告警」和「本次认领的告警」增长，而不是随历史增长。未测量的：`auth_timeout` 汇总里「受影响最多的租户」那条对 `cdrs` 的聚合（每个到期的 `auth_timeout` 告警每个汇总间隔一次，限定 `received_at >= 告警开始` 与 7 天的 `started_at` 下限做分区剪枝，在 PORTALBIG 上的耗时待 PR 6 的详情查询一并测）。
